# v0.2: encrypt your own message in the browser

## Recommendation

**Do it, on two conditions.** First, the JavaScript engine must produce the same
trace format as the Python engine (schema 1, event for event, metadata and all),
so conformance is checked by deep-equality on traces, not by comparing
ciphertexts. Second, the trace player stays exactly as it is: it consumes traces
and does not care which engine made them. Under those conditions v0.2 is about
150 lines of engine, a node test file, and one new page section.

**Why bother.** v0.1 already makes a shareable page. What it cannot do is let a
reader put *their* key and *their* words in, and the lesson that lands hardest
in section 4 (key reuse) lands harder still when the two cancelling messages are
ones the reader typed. Live execution also allows a hand-check mode: shuffle a
physical deck, type its order in, and watch the page walk *your* deck, round by
round. That is the promise the cipher makes, and no precomputed page can keep it.

**Why not, and why the answer is still yes.** Two implementations of one
algorithm will drift; that is the whole thesis of this package. A second engine is
only acceptable because the trace format already exists as a machine-checkable
oracle: if the JS trace differs from the Python trace anywhere (a different
`affected` index, a different `wrapped` flag, a different card), CI fails. That
is a stronger guarantee than most single-implementation projects have. Pyodide
(one engine, in WebAssembly) was considered and rejected: ~10 MB and a
multi-second cold start for a card trick, hostile on the phone the link is most
likely opened on.

**Scope discipline.** The conformance harness is the deliverable. The UI is
secondary. If time runs short, ship the engine and the harness with a minimal
form; polish later.

## Architecture

```
web/
  engine.js     NEW  pure functions mirroring steps.py; emits schema-1 traces
  live.js       NEW  the "Try it" section: form, validation, wiring to the player
  player.js          unchanged; draws whatever trace it is handed
  index.html         gains one section that imports live.js
tests/conformance/
  conformance.test.mjs   NEW  node --test; no npm dependencies
  smoke.json             NEW  five checked-in decks with full Python traces
scripts/
  gen_conformance.py     NEW  emits the full vector set at CI time (not committed)
```

### engine.js

Same five functions, same names, same signatures in spirit:

```js
moveJokerDown(deck, joker, count) -> { deck, phase, affected, meta }
tripleCut(deck)                   -> ...
countCut(deck, count?)            -> ...
outputCard(deck)                  -> ...
generate(deck, length)            -> { values, finalDeck, trace }
passphraseDeck(passphrase, deck?) -> { deck, trace }
encrypt(text, deck)               -> { text, keystream, finalDeck, trace }
```

Decks are arrays of card codes (`"AC"`, `"JA"`), the same encoding the wire
format uses, so a JS trace serializes to JSON identical to `to_dict()` in
Python with no translation layer. Card values come from one table, mirroring
`cards.py`. `meta` dictionaries carry exactly the keys Python's do, including
`output_value` and `output_letter`; anything Python adds later must be added here
or conformance fails, which is the point.

The architecture test that today forbids cipher knowledge in `player.js` gains a
second rule: `engine.js` is the *only* file under `web/` permitted to contain it.

### live.js

One section, "Try it", between sections 3 and 4:

- **Key**: a passphrase field, or "shuffle a deck for me"
  (`crypto.getRandomValues`, never `Math.random`), or paste 54 card codes.
  Validation reuses the same rule as `validate_deck`: 54 codes, each exactly
  once, both jokers present, with the error naming what is missing or doubled.
- **Message**: a text field. Normalization and X-padding match `codec.py`.
- **Encrypt** produces a layers table (plaintext / keystream / ciphertext) and
  hands the trace to a fresh `TracePlayer`, so the reader steps through their
  own encryption exactly as they stepped through the canned one.
- **"Encrypt a second message with this same deck"** re-runs section 4's
  cancellation on the reader's two messages. This is the feature that justifies
  v0.2.
- **Hand-check mode**: paste a physical deck's order; the page prints the deck
  after each round, mirroring `solitaire-lab worksheet`.

Explanations: `live.js` cannot ship Python-authored text for a trace that did
not exist at build time. The headline table already lives in `player.js`; the
per-step sentences move into a small `explain.js` that `live.js` imports and
that a Python test renders against the same events to assert identical output.
This is the one place wording is duplicated, and it is checked.

Permalinks encode the deck (54 codes, ~160 characters) only when the reader
clicks "link to this deck". Plaintext never goes in a URL automatically.

## Conformance

`scripts/gen_conformance.py` produces, deterministically from fixed seeds:

| Set | Count | What is compared |
|---|---|---|
| Random decks, 40-letter keystream with trace | 300 | full `to_dict()` trace, deep-equal |
| Passphrase keyings, random 1–20 letter phrases | 100 | keyed deck + keying trace |
| Encryptions, random deck and 1–60 letter message | 100 | ciphertext, keystream, trace |
| Published vectors (`tests/vectors/published.json`) | all | ciphertext / keystream |
| Edge decks: joker on bottom, jokers adjacent, joker on top | 12 | full trace |

The full set is ~40 MB of JSON and is generated at CI time, not committed.
`tests/conformance/smoke.json` holds five decks with complete traces and *is*
committed so the node tests run locally without Python.

`conformance.test.mjs` uses `node --test` and `assert.deepStrictEqual` on the
parsed objects. Failure output names the deck seed, round, phase, and the first
differing key.

CI gains one job: install package → `python scripts/gen_conformance.py` →
`node --test tests/conformance/`. Node 20+ is on every GitHub runner; no
`package.json` is needed.

## Sequence

1. `engine.js` + smoke conformance against the five committed traces. Stop
   here until the smoke set passes byte-for-byte.
2. `gen_conformance.py` + the full node suite + the CI job.
3. `explain.js` extracted from the build-time sidecar, with the cross-language
   wording test.
4. `live.js` minimal: passphrase + message → layers table + player.
5. Second-message cancellation, shuffle and paste-a-deck inputs, hand-check
   mode, deck permalinks.
6. Architecture test update; README section; republish.

Each step leaves `main` deployable. Steps 1–2 are the risk; 3–6 are UI.

## Acceptance

- Every conformance set passes in CI on Node 20 and 22.
- All three published vectors reproduce from `engine.js` alone.
- `player.js` still contains no cipher knowledge (existing test, unchanged).
- The page with the live section still loads in under 100 KB before fonts
  and shows no horizontal scroll at 390 px.
- A reader can encrypt two messages under one passphrase and see
  `C1 − C2 = P1 − P2` on their own words.

## Non-goals

Decryption UI (it is the same form with a minus sign; add only if asked),
saving messages anywhere, a "share this ciphertext" feature, and any attempt to
present the live tool as more than a teaching instrument. The warning banner
stays above the fold.
